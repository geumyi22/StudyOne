# Phase 30 — 앱 클라이언트 동기화의 정확성 보강

이번 단계는 OAuth·백업·오프라인 대기열을 다시 추가하는 작업이 아닙니다. 이미 구현된 Android, iOS, Windows 앱의 동기화 요청에서 **서버가 성공했다는 증거를 신뢰할 수 있는지**, 그리고 **동일 ID 충돌을 사용자에게 숨기지 않는지**를 수정했습니다.

## 수정한 실제 위험

1. 이전 코드 일부는 POST가 HTTP 200을 반환하고 `changes` 개수만 맞으면 동기화 완료로 처리했습니다. 이는 서버가 잘못된 ID·수정 버전·적용 순서·커서를 반환하더라도 성공으로 표시할 수 있는 결함이었습니다.
2. 업로드는 기존 서버 ID를 안전하게 건너뛰지만, **같은 ID에 서로 다른 내용이 있어도** 사용자가 모른 채 완료됐다고 생각할 수 있었습니다.
3. 특히 Windows는 동기화 승인 전후에 저장된 원본을 다시 확인하지 않았습니다. 사용자가 승인 중 변경한 로컬 기록이나 다른 기기의 서버 변경으로 미리보기와 전송 내용이 달라질 수 있었습니다.

## 개선한 기능

- **Android**: `verifyChangeAck`가 HTTP 200만이 아니라 요청 건수, ID, 종류, `baseRevision+1`, 삭제 여부, 증가하는 순서 번호, 마지막 서버 커서, 서버 시각을 각각 검사. 기존 신규 업로드와 대기열 재전송에 동일 함수 적용.
- **iOS**: 동일한 서버 변경 승인 검증을 Swift `verifyChangeAck`에 구현, 두 전송 경로에 연결.
- **Windows**: 변경 응답의 6가지 필드·순서·최종 커서를 검증하고, 기존 업로드와 대기열 재전송 모두에 적용.
- **세 플랫폼 비교 UI**: 읽기 전용 화면에서 서버에만 있는 신규 ID, 로컬에만 있는 ID, 동일 내용 ID, **같은 ID의 다른 내용(충돌)**을 명확히 표시. 계정·개인 기록은 서버로 업로드하지 않음.
- **업로드 차단**: 동일 ID에 다른 내용이 있으면 신규 업로드를 시작하지 않고 개별 검토를 요청. Android/iOS/Windows 모두 사용자 승인 중 서버 `cursor`가 바뀌면 다시 확인하도록 차단. Windows는 로컬 원본 바이트와 승인한 신규 변경 목록도 재검증.
- 모든 처리 과정에서 **서버 또는 앱의 기존 기록을 자동 덮어쓰거나 삭제하지 않음**. AI가 독단적으로 충돌을 해결하지 않음.

## 검증 범위

- Windows .NET 테스트: 정상이면서 순서가 맞는 합성 승인 응답을 통과시키고 위조 ID·수정 버전·커서·중복 seq를 거부.
- Android 에뮬레이터에 연결된 독립 합성 `selfTest`: 동일한 네 가지 오류를 거부.
- iOS Swift 합성 `selfTest`: ID·revision·cursor 변조 거부, Debug/Simulator 타입 검사.
- 기존 앱 백업, 복구, 학습 진도, AI 승인, 서버 계정 격리 회귀 CI 유지.
- 실기기에서의 운영 서버 및 실제 ChatGPT 계정 연결은 이번 변경으로 완료되지 않았음.

## 남은 사용자 가치 작업

향후에는 실제 Android/iOS/Windows 앱을 각 기기에서 띄워 동일 무료 로컬 TLS 서버에 연결하고 화면 조작 E2E를 검증해야 합니다. 유료 호스팅 없이도 로컬 E2E는 가능하지만 Android/iOS/Windows 네트워크·인증서 설치 등의 환경 구성은 추가 작업입니다. OAuth 사용자의 개인 계정 연결·동의, 충돌 발생 시 명시적인 항목별 선택 UX, 수정·삭제 이력 양방향 병합, 오프라인 자동 동기화는 미완료입니다.

공개 Stable/Beta 앱을 릴리즈하거나 실제 사용자 파일·계정·GitHub secrets를 변경하지 않았습니다.
